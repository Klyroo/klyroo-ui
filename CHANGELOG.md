# Changelog

All notable changes to Blux.UI are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows
[Semantic Versioning](https://semver.org/spec/v2.0.0.html) (while below 1.0, a minor version may contain breaking changes).

## [Unreleased]

### Changed

- **The data list docs are five pages.** `/components/data-list` keeps the basics (memory, provider, URL, search, large first page, error); `data-list-filters`, `data-list-filter-panel`, `data-list-facets` and `data-list-selection` hold the rest, so no page hands a state close to the 32 KB the client can send back to the server when a Server or Auto circuit starts. The old anchors of the moved examples no longer exist on `/components/data-list`.
- **The Dashboard template's customers table uses the built-in selection and actions** instead of its own `RowSelection` and select-page checkbox: the bulk delete is a `DataListAction` with a confirmation, the rows that leave the query leave the selection.

### Fixed

- **`BLUXTOOLS001` only fires where it means something.** The warning that Blux.UI.Tools needs Tailwind compiled by the app was raised in every project the package reached, hosts with no Tailwind included, which had to set `BluxToolsOwnTailwind` to silence it. It now fires in the project that has a `PackageReference` to Blux.UI.Tools and in a project that compiles Tailwind with Node (a `package.json` with a `tailwindcss` or `@tailwindcss/*` dependency; `prettier-plugin-tailwindcss` alone does not count); a project that only reaches the package through another one is left alone. `BluxTailwind` and `BluxToolsOwnTailwind` still silence it. The Dashboard template no longer sets `BluxToolsOwnTailwind` in its Web, Web.Client and Maui projects.
- **A sidebar renders its content once.** `BxSidebar` and `BxDashboardSidebar` used to render `Header`, `ChildContent` and `Footer` twice (the column and a `BxSlideover` copy), so ids, test ids, radio group names and component state existed twice. The `aside` is now the one element: from lg it is the column, below lg it is an off-canvas panel built on the popover API (`popover="auto"`, `popovertarget`, `::backdrop`, a slide-in that respects `prefers-reduced-motion`), made modal by the browser while it is open (the page behind is inert, Tab stays inside, Escape and a click on the backdrop close it, the focus goes back to the button, a screen that grows past lg closes it). The dialog role and `aria-modal` sit on an inner `data-slot="panel"` element, so the aside stays a complementary landmark and passes axe open. A form submitted in the panel, or a navigation to another path, closes it; a modal declared in the sidebar works in place and keeps the panel open; a modal declared outside it (the appearance dialog of a layout) closes it, and the focus returns to the button when that modal closes. After an enhanced navigation merge the modal state is rebuilt. The title and the close button are inside the aside and shown below lg only; opening needs no round trip, and `BxDashboardSidebarToggle` names the panel from the server (`bx-sidebar-{Id}`), so it opens with no script at all. The collapsed styles of the theme apply from lg only. `SidebarUi.MobileBody` is replaced by `Panel`, `MobileHeader`, `MobileTitle` and `MobileClose`.
- **A static date filter form no longer drifts.** The `datetime-local` field of a timed date filter is written in the time zone of the cookie, but the posted value was read as UTC, so with a `Europe/Paris` cookie a 13:00 UTC bound showed 14:00 and was applied again as 14:00 UTC (one hour further on every apply), and a whole-day bound came back as a one-minute instant at UTC midnight. A date-time without an offset in a filter value is now the wall clock of the time zone of the request (`DataListStateQuery.FromQuery(query, schema, prefix, timeZone)` and the data list; without a zone it stays UTC, as before for API servers), and a whole-day bound is rendered in a date field, which reads back as the same whole day.
- **A remote option resolve that outlives a source change no longer poisons the new source.** `RemoteOptions.Reset` (a new `OptionsKey` of `BxSelectMenu` or `BxInputMenu`) now cancels the `ResolveSelected` call in flight and ignores its answer or failure, so a late answer for the old source cannot write a stale label that stops the value from being resolved again.
- **The start of a day that begins in a daylight saving gap is the same instant on the server and in the editor.** `DateUnit` stepped 30 minutes over a gap (01:00+14:00 for the skipped 2011-12-30 in Pacific/Apia, or 01:00 for a 45-minute gap) while the filter editor found the exact end of the gap; both now use one rule (`LocalInstants` in Blux.UI.Tools.Query), so a skipped day is an empty range that ends where the next day starts.
- **`BxSelectMenu` and `BxInputMenu` throw about missing options only when `Items` is not passed at all and there is no `OptionsProvider`.** `Items="@_list"` with a null list (still loading) renders an empty list, before and after the list arrives.
- The data list calls `SetLoadedTimeZone` once, not twice, when it adopts the prerendered result.

### Added

- **Data list selection and actions.** A list with a `BxDataListSelectionActions` bar (or `Selectable`, or a bound `SelectedKeys`) shows a checkbox column: a box per row named "Select {RowLabel}" (or "Select row {n}"), a select-all box in the header with the mixed state, Space on a box and Shift+click for a range over the rows on screen. `@bind-SelectedKeys` holds the row keys as strings. A list in memory (`Items`) keeps the selection across pages while the search and the filters still match the rows (`SelectionScope.Auto`, or `Page` to keep only the page); a `Provider` or a `Queryable` keeps the rows of the page. `BxDataListSelectionActions` is a bar that sticks to the bottom of the list (or is fixed): the count in a live region, "Select all N results" when the source returns a total, the `DataListAction`s (label, icon, color, `Visible`, `Disabled`, `Confirm` with a dialog whose text can count the rows, `ClearSelection` never, on trigger or on success, `RefreshOnSuccess`, `OnExecute`), a "More actions" menu past `MaxVisible` and Clear selection. An action gets a `DataListActionContext` with the selected items and keys, the scope (`Selection` or `All`), the matching count and the `DataListRequest` of the query without paging, so an every-result action over a provider sends the request to the server instead of the rows; a running action shows a spinner and cannot start twice, and a failure keeps the selection and goes to `OnError`. `BxDataListActionsDropdown` holds toolbar actions. Interactive only: a statically rendered list draws no checkbox column, bar or menu (a prerender of an interactive page keeps the column with disabled boxes). `DataListActionContext.TargetCount` is the number of ticked rows, or the matching count under every result: use it in a confirmation and in `Visible` and `Disabled`. `ClearSelection.Success` unticks only the rows the action targeted, and the focus goes to the select-all box when the bar leaves with the focused button. The bar is sticky by default; the list shows no toasts of its own. Messages in the 12 locales (en and fr reviewed), new theme slots.
- **`BxDates`: the date format of the content components, public.** `BxDates.Format(date, format?, culture?)` writes the long date of the culture without the day name (or `format`), `BxDates.Iso(date)` is the `datetime` value of a `time` element, and `BxDates.FormatCulture()` is the culture components use when they have no `Culture` parameter (the regional current culture when it has the language of the locale in effect, otherwise the culture of the locale). `BxBlogPost` and `BxChangelogVersion` use it, and the SaaS template drops its copy (`SiteDates`). `FormatFor(date, locale, format?)`, `FormatCulture(BxLocale)` and `FormatCulture(BluxOptions)` follow the locale the way the components do (the cascading locale, `BluxOptions.Locale`, then the UI culture); the parameterless one only knows the built-in locale of the UI culture and says so.
- **`BxDashboardNavbar` takes `As` and `HeadingLevel`.** `As="div"` renders a div instead of the `header` element and `HeadingLevel` sets the level of the title (1 by default), so a second navbar on a page (the detail panel next to a list) adds neither a second banner landmark nor a second h1. The defaults keep the output of a single navbar. The Dashboard template's inbox detail navbar uses `As="div"`. `As` accepts "header" or "div" in any case (a missing value is the default) and throws an `ArgumentException` otherwise; `BxPageAside.As` ("aside" or "div") is validated the same way, and `BxSidebar.As` is case-insensitive too.
- **Data list facets: counts next to the options of option and boolean filters, and option filters that load their options from a remote source.** `DataListFilter.WithFacets()` now also works on a boolean filter (Yes and No show their counts, `Yes (13)`), and the include empty switch of an option filter shows how many rows have no value. `WithFacetMode(FacetMode.IncludeSelf)` keeps the filter's own rule in its counts (the default leaves it out), `WithOptionSort(DataListOptionSort.Count|Alpha)` orders the options and `WithOptionLimit(n)` lists the first ones with a "Show N more" button (a selected option is never held back; a statically rendered editor lists them all). The counts are asked for when the filters, the search or the time zone change and are kept while the user pages or sorts: `DataListController` sends the next request without `Facets` and puts the facets of the result on screen into the new result (a refresh asks again), so a database or an API does not count again on every page; a prerendered result carries its counts and they count in the persisted size. `WithRemoteOptions(provider, resolveSelected, pageSize, minLength)` loads the options of an option filter page by page (`DataListOptionsRequest`, `DataListOptionsPage`, `DataListOptionsProvider`, `DataListOptionsResolver` in `Blux.UI.Tools.Query`), reusing the paging, search, cancellation and error state of the remote `BxSelectMenu` (`BxDataListFilterEditor` loads the first page when it is shown, searches after a pause in the typing, loads the next page as the list scrolls and shows an error with a Retry button). Values restored from the address are labelled by the resolver (on the server in a static render and a prerender, in the browser once interactive) and a picked option brings its label at once, so a tag reads `Customer is Globex (Cypress Creek)`; the options that are listed carry the counts of the facet. A statically rendered remote editor lists the selected and the counted options and says that searching the rest needs JavaScript (`FilterOptionsNeedScript`, `FilterOptionsMore`: new messages in 12 locales, French reviewed, the others to review). The remote options engine is public API of `Blux.UI`: `BxRemoteOptions` and `BxRemoteStatus` (paging, search, cancellation, error and retry of a `BxOptionsProvider`), used by `BxSelectMenu`, `BxInputMenu` and the data list editors, with no `InternalsVisibleTo` to the companion packages. The counts of the options a remote editor lists are asked for by value (`DataListFacetRequest.Values`, supported by the in-memory executor and by the IQueryable/EF facet queries, translated to an `IN` list, exact beyond `MaxFacetBuckets`), the labels the prerender resolved are persisted with its result (they count in the persisted size; nothing is persisted when there are none) so that the interactive render shows them at once and does not ask the resolver again, the labels of the values in the state are resolved while the rows load, a resolver that throws is logged as a warning, a filter panel section or a tag popover loads its remote options when it opens (the add filter menu when the filter is picked), a statically rendered remote editor lists only the counted options it could label (at most `WithOptionLimit`, else the page size, resolved in one call), and `WithOptionSort` does not apply to remote filters. A provider's `Facets` answer `request.Facets`: a request the list sends without facets (a page or a sort) keeps the counts on screen whatever the provider returns in `Facets`, and a page past the end reuses the counts of the first answer. The counts are part of the accessible description of the option checkbox and of the include empty switch. A `Schema` given to `BxDataList` after its first render is ignored (build it once). New live examples (counts, remote options with a 400 ms directory) and a guide, "Data list sources and counts", with the Entity Framework and provider setups.
- **`DataListStateQuery` reads a repeated filter key as one value.** A GET form sends a checkbox per option under one name (`f.status=Paid&f.status=Draft`): an option filter now takes all the repeats (blank ones are skipped, `~` adds the empty rows), any other kind keeps the first value that is not blank plus a repeat that is exactly `~` (include empty rows), and a range sent as `f.key.from` and `f.key.to` takes its include-empty from a companion `f.key.between=~`. The address the app writes is still one comma list. A value-less rule (`is empty`) is `f.key.isEmpty=~`.
- **`BxDataListFilterPanel`: every filter of the schema as a collapsible section, for a sidebar next to the table or the content of a `BxSlideover` on a phone.** Each section holds the `BxDataListFilterEditor` of the filter (new parameter `Embedded`, new cascading draft scope), so the operators, presets, number and date parsing, limits and history rules are the ones of the tags and the add filter menu: no editor logic is duplicated. A section with a filter on starts expanded (and opens when a tag or the address turns one on) and shows how many values are on (selected options, include empty), the header shows the total, and Clear filters takes them all off with one history entry. `ApplyMode=Live` (default) applies each change like the popovers; `ApplyMode=Submit` stages the changes of all sections until Apply (one history entry) and Reset drops them, `CloseOnApply` makes Apply close a slideover around the panel (`data-bx-close`), `Description` adds a line under the title. In Submit, Clear filters stages the removal (Reset restores), and Apply, Reset and Clear stay focusable (`aria-disabled`) so the focus never falls to the page; the panel shows the number of results in a live region. Statically rendered the panel is one GET form and its Apply button sends every field: text, number and date fields (a range as `f.key.from` and `f.key.to`, a whole day as a date field in the time zone of the `blux-timezone` cookie), a checkbox per option and Yes / No / Any radios, with only the operators left as links; a rule the form cannot edit (is empty, or include-empty written in the address) goes back as it came, and the script of Blux.UI.Tools leaves blank fields (of filters without a default rule) out of the address. New messages `FilterPanelTitle`, `FilterPanelActive`, `FilterPanelResults`, `FilterPanelNone`, `FilterReset` in the 12 locales (en and fr reviewed), new theme slots `filterPanel*`, docs examples "Filter panel" and "Filter panel in a slideover" (the recommended responsive pattern).
- **`BxDataListColumn.HeaderTemplate`**: the content of a header cell, instead of the title and the sort control. It renders inside the list, so a part derived from `DataListPartBase<TItem>` works in it: a select-all checkbox that knows the rows of the page, or a header that is only an accessible name (`<span class="sr-only">Actions</span>`) for a column of buttons. Used by the Dashboard template.
- **`Blux.UI.Server`: a package that lets components read the request in a static render or a prerender, and `IBxRequestCookies` in Blux.UI.** `IBxRequestCookies` (`PathBase`, `Get(name)`) is the only way Blux reads a cookie of the current request; nothing implements it by default, so WebAssembly, MAUI and an interactive render after a prerender have no request. `services.AddBluxServer()` (package `Blux.UI.Server`, ASP.NET Core only, same version as Blux.UI) calls `AddHttpContextAccessor()` and registers it. The data list reads the `blux-timezone` cookie through it, and the reflection on `IHttpContextAccessor` is gone from Blux.UI.Tools, which no longer registers the accessor: a server app must call `AddBluxServer()` in its server `Program.cs` for static and prerendered lists to use the time zone of the user. Without it they use UTC until the page is interactive, and Development logs one warning.
- **Review fixes of the remote options of `BxSelectMenu` and `BxInputMenu`, and `OptionsKey`.** The labels of the values that `Items` names (and the ones resolved) now go to the browser in every render mode (`data-known`), so a statically rendered or prerendered field keeps `France` instead of the browser writing `fr` over it. With `Create`, the option that creates the typed text is decided again when the answer arrives (it no longer stays next to the exact option the source returned), and a text that is already a value shows "No results" instead of an empty list. A text that trims to the one already answered (a trailing space, a letter typed and deleted within the pause) asks nothing and gives the highlight back, so Enter works. On reopening, the previous options stay visible but nothing is highlighted until the fresh answer arrives, so Enter cannot pick a stale option. New `OptionsKey` (`object?`, compared with `Equals`): when it changes the loaded pages, the search text, the cursor and the resolved labels are forgotten, the selected values are resolved again, and the list loads again the next time it opens; a new delegate with the same key keeps what was loaded (docs example: the cities of a country). A `ResolveSelected` that throws keeps the raw values and is tried again the next time the list opens. `BxSelectMenu` and `BxInputMenu` throw an `InvalidOperationException` naming both parameters when neither `Items` nor `OptionsProvider` is set. The four new messages are marked as drafts in the ten locales that are not English or French, and `BxLocales.ReviewedCodes` lists the reviewed ones.
- **`BxInputMenu` loads its suggestions from a remote source too, with the same `OptionsProvider`, `ResolveSelected`, `Debounce`, `MinLength` and `PageSize`.** Typing searches the source (the text is trimmed, sent after `Debounce` ms, only with `MinLength` characters) and the matches replace the list; a free text field searches what it holds when the list opens, a `Strict` field searches the empty text then (it always lists everything). Paging, cancellation of stale requests, the loading, no results, short text and error states (polite status, `role="alert"`, Retry, Enter retries) and the scrolling area with `BxInfiniteScroll` are those of `BxSelectMenu`, from the same internal class. `ResolveSelected` names a `Strict` value no page contains (the field shows its label; without it, the raw value), and the browser keeps that label when a later search drops the option, so leaving the field puts it back. **Interactive only:** a statically rendered page (and the prerender) never calls the provider: a free text field is then a plain text field with no suggestions (`data-inert-list` keeps the browser from opening an empty list), a `Strict` field shows its value as given, read only, and posts it. `Items` is optional with a provider, and names values without listing them. New slots `Scroller`, `Loading`, `Spinner`, `Error` and `Announcer` of `InputMenuUi`. Docs: two examples on the InputMenu page with the simulated source.
- **`BxSelectMenu` loads its options from a remote source: `OptionsProvider`, `ResolveSelected`, `Debounce`, `MinLength`, `PageSize`.** `OptionsProvider` is a `BxOptionsProvider` (`BxOptionsRequest(Search, Skip, Take, Cursor)` and a `CancellationToken` in, `BxOptionsResult(Items, HasMore, NextCursor)` out): page it with `Skip` and `Take`, or with a cursor (a non-null `NextCursor` also means there is a next page). The browser stops filtering and the filter field searches the source: the text is trimmed, sent after `Debounce` ms (250 by default) of quiet, and only when it has `MinLength` characters (0 by default; a shorter text shows a hint and lists nothing, an empty text lists the unfiltered options). Opening the list searches the empty text; an older request is cancelled and an older answer never replaces a newer one; the options of the previous text stay listed (and the list is `aria-busy`) until the new ones arrive. The next page (`PageSize`, 25 by default) loads as the list scrolls, one list height before its end, through `BxInfiniteScroll` placed beside the listbox in the scrolled area, and by its "Load more" button. `ResolveSelected` names the selected values that no loaded page contains (values restored from the address or a saved form), once per value as soon as the component is interactive; without it, or for a value it does not return, the field shows the raw value. The label of a selected value survives a search that drops its option (the browser keeps it, and `data-known` seeds it). Loading, no results, text too short and failure each have a state with a polite status (`role="status"`); a failure shows a translated `role="alert"` message with a Retry button (Enter in the filter field also retries). **Interactive only:** a statically rendered page (and the prerender before the page becomes interactive) never calls the provider, renders the current values as raw values (or as the labels of `Items`, which with a provider are not listed but name values), keeps posting them, and disables the trigger, since the list would open empty. `Items` is no longer `[EditorRequired]`: it is optional with a provider. New browser event `bx-search` (`onbxsearch`, `BxSearchEventArgs`), new slots `Scroller`, `Loading`, `Spinner`, `Error` and `Announcer` of `SelectMenuUi` and the theme (with a provider the list scrolls in `scroller` and no longer in `listbox`), and four messages in 12 locales (`RemoteOptionsLoading`, `RemoteOptionsError`, `RemoteOptionsRetry`, `RemoteOptionsMinLength`). The loading logic is one internal class shared with `BxInputMenu`. Docs: three "Remote options" examples on the SelectMenu page with a simulated source (400 ms per call).
- **A data list hands its prerendered result to the interactive render only when it is small.** The client sends everything persisted to the server when a Server circuit starts and SignalR refuses a message past 32 KB, so a page with big first results never became interactive. `BluxToolsOptions.PersistMaxBytes` (16 KB by default, per list: state, loaded state and result with its facets as JSON) and `PersistPageMaxBytes` (8 KB for the lists of a page together, in the order they persist: what the browser sends is about 3.5 times bigger once escaped, encrypted and encoded) decide; a list over a limit is not persisted, a warning names it and its size, and the interactive render loads it once.
- **Filter UI for the data list: `BxDataListFilterTags`, `BxDataListAddFilter`, `BxDataListClearFilters` and `BxDataListFilterEditor`, for text, option and boolean filters.** One tag per active filter reads "Status is Paid, Pending +2" (operators localized in the 12 languages), opens the editor of the filter in a `BxPopover` anchored to the tag, and has an x named "Remove filter Status"; the tags are a list named "Filters, 2 active". `ShowAdd` adds the Add filter menu (the filters not on yet, with a search field above 8; picking one opens its editor), `ShowClear` adds Clear filters (also usable alone: it takes every filter off, not the search), and a schema with filters gets all of it in the default layout. The editors: a text filter has an operator select (the operators the filter allows) and a `BxInput` with the `SearchDebounce` pause; an option filter has an operator select (`is any of`, `is not`; `is` when the rule uses it), a search field, a checkbox per option with its count, and an "Include empty values" switch that maps to `IncludeEmpty` and the `~` token; a boolean filter is a Yes / No / Any group. `ApplyMode` (`Live`, the default, or `Submit` with Apply and Cancel) says whether changes apply at once. Each applied change is a history entry and goes back to page 1, so Back undoes one filter change; the typing of one text stays in the entry its first pause made. `DataListFilter.Option(...)` takes the options to list (`DataListFilterOption(value, label)` or plain values), `WithLabel` names a filter (else the title of the column with that key, else the key written as words) and `WithFacets` asks for the option counts with each load (the counts leave out the filter's own selection). Statically rendered, the tags' x, the operators, the options and the Yes / No / Any choices are links and a text filter is a GET form (`data-enhance`); opening a popover needs the script of Blux.UI but no .NET, and an operator can only be changed once the filter has a value. Number and date filters have their own editors (see the next entry). New theme slots in `BluxToolsOptions.DataList` (`filters`, `filterTags`, `filterTag`, `filterEditor`...), 36 new messages in 12 languages, docs examples ("Filters", "Filters, Submit mode") and E2E tests in the four render modes.
- **Number and date filters in the data list filter UI.** A number filter has the seven operators (`is`, `is not`, `is greater than`, `is at least`, `is less than`, `is at most`, `is between`) and edits with `BxInputNumber` (the `Min`, `Max` and `Step` of `DataListFilter.Number`) and, with the new `WithNumberDisplay(DataListNumberDisplay.Slider | InputAndSlider)` and both limits set, a `BxSlider`; a range has From and To fields (either can stay empty) and a `BxRangeSlider`. A date filter has `is`, `is not`, `is before`, `is after` and `is between`: a single day is a `BxInputDate`, a range a range `BxCalendar` (the second click applies; the first applies nothing), and a filter exact to the hour or minute (`DataListFilter.Date(DateGranularity.Minute)`) adds a `BxInputTime` and filters on the instant in the time zone of the user. Presets by operator (Today, Yesterday, Start of month, 7 days ago, Start of year; for a range Today, Last 7 days, Last 30 days, This month, Last month, Year to date) are computed in the time zone of the user, which the list takes from the browser once it is interactive (UTC before that and in static rendering), from the `TimeProvider` of the app. `WithMaxRangeDays` limits a range in the editor only (the calendar leaves out the days beyond it; the URL and the server do not check it), and `WithNumberFormat` sets the .NET format of the numbers in the tag; tags write numbers and dates in the culture of the user (`Amount is between 1,000 – 2,000`, `Day is 11/3/2026 – 11/9/2026`), moments in the time zone of the user. Changing the operator between a single value and a range keeps the value (it becomes the start of the range). A date filter exact to the second keeps its tag and applies but has no editor. Statically rendered the operators and presets are links and a number or date is a GET form with native `number`, `date` or `datetime-local` fields; a range sends two fields, `f.<key>.from` and `f.<key>.to`, which `DataListStateQuery` now reads as `f.<key>.between` (a GET form cannot write `from..to` in one field; the app always writes the canonical key back). No slider without the script and .NET, and a filter that is not on yet starts with its default operator (switch it from the tag). **The time zone of the browser reaches the server in a cookie**: the script of Blux.UI.Tools writes `blux-timezone` (`blux-timezone.{slug}~~` below a path base, whose path it is scoped to; SameSite=Lax, about 13 months, the new public `BxPathScope.CookieName` names it) and static renders and prerenders read it, validated against the zones of the machine, so their days, presets and tags are the user's; the first visit, before any script ran, and an unknown zone fall back to UTC. A prerendered result is adopted by the interactive render only when its days were cut in the zone of the browser (any day or instant in a rule counts), else the list loads once more. A single day, from a preset or picked without a time, covers the whole local day on a timed filter too (`is Today` is today 00:00 to tomorrow 00:00, `after Today` starts tomorrow); picking a time makes it an instant. 21 new messages in 12 languages (English and French reviewed, the others drafts), new `filterRange`, `filterRangeSlider`, `filterPresets`, `filterHint` and `filterPopoverWide` slots, docs examples ("Number filters", "Date filters") and E2E tests in the four render modes.
- **`BxInfiniteScroll`**: a "load more" point for a list that grows (feeds, option lists, chat history, the cursor mode of a data list). An `IntersectionObserver` in the browser watches a sentinel and `OnLoadMore` runs once each time it comes into view, and not again until the load is over: `Loading` turning false, or the `OnLoadMore` callback returning (an async handler counts as running, so it needs no flag), looks at the sentinel again, so a sentinel still in view after the new items asks for the next ones. `HasMore` ends it (the sentinel and the button go away, "No more items" is announced and `ShowEnd` shows it), `RootMargin` (default `0px 0px 200px 0px`; for a list that loads upward put the component first with `200px 0px 0px 0px`) and `Root` (a CSS selector, which warns in the console and watches the viewport when it matches nothing; by default the closest ancestor that really scrolls, never a wrapper whose `overflow-y` is only computed as `auto` because of an `overflow-x-hidden`, else the viewport) say where to watch. A load that adds nothing (or throws) is not asked again until the sentinel has left the view and come back, or the button is used, so a sentinel that stays in view cannot loop: a handler that has nothing more should set `HasMore` to false, or show a retry. The component does not set `aria-busy` (it would hide its own announcement): put it on your list. A "Load more" button is always there for keyboards, screen readers and browsers without `IntersectionObserver` (the focus goes to a plain marker element, not the live region, when the last one disappears); without a listener (static rendering, or before the page is interactive) it is a link to `Href`, so the next page or cursor URL works without scripts. Loading and the end are announced politely (`role="status"`), the spinner stops under `prefers-reduced-motion`, and its three texts are translated in the 12 locales (`LoadMore`, `LoadingMore`, `NoMoreItems`). It uses the `bx-change` event, so it works in every render mode and in a web view. New `infiniteScroll` theme slots (`root`, `sentinel`, `trigger`, `spinner`, `status`, `end`, `marker`).
- **`BxSelectItem` gets `Count`, `Icon` and `Group`**, in `BxSelect`, `BxSelectMenu`, `BxInputMenu` and `BxListbox` (and so in `BxLocaleSelect` and the select fields of `BxAuthForm`). `Count` is a number at the end of the row (matches, stock, unread), formatted for the locale and neither searched nor typed ahead; `Icon` is an icon by name before the label; `Group` lists items under a heading: the items without a group come first, in their order and with no heading, then each group in the order of its first item. A group is `role="group"` named by its heading (`aria-labelledby`), the heading is not an option, so the arrow keys, Home, End and the typeahead skip it, and in `BxSelectMenu` and `BxInputMenu` the filter hides a heading with its last matching option. `Count` follows the label in the accessible name of the row, after a visually hidden ", " (also in `BxCommandPalette`: `BxCommandItem` gets `Count` too, before the shortcut), and the closed `BxSelect` and `BxSelectMenu` trigger shows the `Icon` of the selected item (not the count; a multiple `BxSelectMenu` shows none). ### Changed

- **`Blux.UI.Tools.Query` in-memory ordering by row key.** Ties in a sort are now broken by the row key compared by its own type (2 before 10, a string key ordinal) in every paging mode, not by its text and only for cursor paging, so a database that orders the key the same way gives the same pages; the cursor's key is parsed back to the key type. A schema without a row key still keeps the input order of ties. A row key a cursor cannot carry (an object, a custom struct) now throws `InvalidOperationException` instead of failing in the comparer.
- **Path bases.** Apps served below a path base (`UsePathBase("/x")` with `<base href="/x/">`), alone or next to other Blux apps on one origin, work: the local image endpoint default is now relative (`BxLocalImageProvider.DefaultEndpoint` = `_blux/img`, was `/_blux/img`) so the browser resolves it against `<base href>`; an endpoint that starts with `/` is still used literally. Below a path base (never at the root, where nothing changes) the sidebar cookies are scoped to the base path and named `blux-sidebar.{slug}~~{id}` instead of `blux-sidebar-{id}` (`BxPathScope.SidebarCookieName(id, Request.PathBase)` gives the name for a server that reads it; cookies written before at `path=/` are not migrated), and the Blux localStorage keys (dashboard panel sizes, banner dismissals, the stored culture of a web view) get the base path as a prefix; the color mode key stays shared on the origin. The culture cookie stays one for the origin, at `path=/` (`BxLocaleSelect.CookiePath` still defaults to `/`). Scoping only applies when the page has a `<base href>`. `BxHeader.Href` and `BxError.Href` default to `./` instead of `/`, so they follow `<base href>`.
- The bottom safe area inset is applied once: `BxFooter` owns it, `BxMain` only when no footer follows (`data-bx-main`), and `BxDashboardGroup` not inside a `BxMain`. `BxSwitch` wraps its track in a label. `BxLocaleSelect` keeps a choice made in a web view when its parent renders again.
- `BxLocaleSelect.Reload` is now `bool?` (unset: reload in a browser, no reload in a web view).
- `BxHeader`, `BxMain`, `BxFooter`, `BxPageAside`, `BxDashboardGroup`, `BxSlideover`, `BxDrawer` and the toaster add safe area padding (zero unless the page draws under the system bars).

- **Icons**, like the icon system of Nuxt UI. Any Iconify icon works by name: `i-{collection}-{name}` (`i-ph-house`), `{collection}:{name}` (`ph:house`) or a bare Lucide name. The Lucide icons that components use are embedded (generated from `@iconify-json/lucide`, ISC notice kept); the build bundles every other icon the app writes as a literal: the `BluxResolveIcons` task scans `.razor`, `.cshtml` and `.cs` files, downloads missing icons from the Iconify API into a per-icon cache (`obj/blux/icons-cache`) and generates a module initializer that registers them, so nothing is requested at run time and it works in every render mode, trimmed or not. `<BluxIcon Include="ph:cube;ph:cube-fill" />` lists names the scan cannot see, `<BluxIconCollection Include="Assets/icons" Prefix="custom" />` makes a folder of SVG files a collection, `BluxIcons=false` turns it off, `BluxOffline=true` builds from the cache. A missing icon is a warning in Debug and an error in Release. See the Icons guide.
- `BluxOptions.Icons` has one property per icon components draw, with the 45 keys of Nuxt UI (`Close`, `Check`, `ChevronDown`, `Loading`, `Search`...) plus `ChevronUpDown`, `Calendar`, `Play` and `Pause`: `o.Icons.Close = "ph:x"`. `Register` and `RegisterSvg` add icons in code.
- An icon that cannot be found renders an empty icon marked `data-bx-missing-icon`.
- Icon data is treated as untrusted: every body (Iconify API, cache, folders of SVG files, `RegisterSvg`) is parsed as XML and rewritten from an allowlist of SVG drawing elements and attributes before it is compiled in (no scripts, handlers, images, external links or `url()`). Ids inside an icon (gradients, clip paths, animations) are made unique per drawing. The build tells an unknown collection from an outage and remembers it, only caches "not found" for names the API lists as such, keeps the cache atomic and best effort (`BLUXICON004` warning), versions it, scans only `i-prefix-name` literals outside icon contexts, skips dot folders, links and files over 1 MiB, does nothing when nothing changed, removes the generated file when no icon remains, and registers the bundles of every assembly of the app before the first lookup (Auto render mode).
- **AI tooling**, generated from the docs catalog and the library so it cannot go stale: the `Blux.UI.Mcp` dotnet tool (`blux-ui-mcp`, an MCP server over stdio),
  the same server over HTTP at `/mcp` on the docs site (`X-MCP-Tools` restricts the tools), `/llms.txt` and `/llms-full.txt`, and the `blux-ui` agent skill in `skills/blux-ui`.

The fill, text and on-fill tokens are picked from the shades so the contrast rules hold.
- `o.Defaults.Color` and `o.Defaults.Size`, used by components when the parameter is not set.
- Tokens `--blux-text-toned`, `--blux-text-inverted`, `--blux-bg-inverted`, `--blux-border-muted`, `--blux-border-inverted`, `--blux-container`, `--blux-header-height`, and the chart series colors `--blux-chart-1` to `--blux-chart-6` (with `-text` and `-contrast`), which are unset by default and fall back to the semantic colors at the element.

- Docs: Design system and CSS variables guides, and the ThemeStyle page.
- **Self-hosted fonts**, like `@nuxt/fonts` in Nuxt UI. Declare `<BluxFont Include="Public Sans" Role="sans" Weights="400;700" />` items in the app project: the build downloads the woff2 files from Google Fonts, Bunny Fonts or Fontsource (or reads local files), hosts them as static web assets under `/_blux/fonts/` with content-hashed names, and generates `blux.fonts.css` (`@font-face` with `unicode-range` per subset, a metrics-adjusted fallback face per family, `--blux-font-sans` and `--blux-font-mono`). `BxFonts` links it and preloads the main faces. Cached in `obj/blux/fonts-cache`, offline builds work from the cache, a font that cannot be resolved is a warning in Debug and an error in Release, `BluxFonts=false` turns it off. Provider answers are validated before they are cached (JSON, https URLs, font signatures, `unicode-range` syntax) and a bad answer falls back to the next provider; identical files are stored once; every font extension is served with an immutable `Cache-Control`; declaring fonts in a Blazor WebAssembly project is error `BLUXFONT010`. An explicit `Culture` parameter wins. File sizes, AM/PM, the modifier key of shortcuts and the slash menu of the editor are localized, and the calendar heading and the carousel role descriptions too.
- `BxApp` cascades its locale as a fixed value: a navigation no longer re-renders every component below it. Changing `Locale` re-creates the subtree. `BluxOptions.Locales` is copied when assigned, and `Locale` and `Locales` become read-only when the first locale is resolved (like the themes).
- The sort buttons of Table (tooltip) and the summary of Form (accessible name) use their messages.
